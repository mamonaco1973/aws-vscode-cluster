# AWS VS Code Cluster

This project is a model for deploying **browser-based VS Code** on Amazon Web Services (AWS) the way Posit Workbench does: users sign in to one web page and get a private `code-server` session running under their own identity, with their files on shared storage. Sessions run on an **Auto Scaling Group** of EC2 instances behind an Application Load Balancer, built from a custom AMI.

The piece that makes this work is a small **session broker** written for this project. `code-server` is a *single-user* process whose only authentication mode is a shared password, so pointing a load balancer straight at it would give every user the same identity and the same home directory. The broker runs on every cluster node and supplies the missing multi-user layer:

1. Authenticates the user against Active Directory through PAM and SSSD.
2. Launches a private `code-server` process **as that Linux user** with `systemd-run`, bound to loopback.
3. Reverse-proxies the browser to it, including the WebSocket traffic the editor runs on.
4. Stops the process when the user signs out or goes idle.

Key capabilities demonstrated:

1. **Per-user sessions** – Each user gets their own `code-server` process, in its own systemd unit, reachable only through the broker.
2. **Real POSIX identity** – Every session runs as the user's AD `uidNumber`/`gidNumber`, resolved by SSSD, so files on shared storage have the same ownership everywhere.
3. **Load-balanced cluster** – An ALB with cookie stickiness spreads users across the nodes; the group adds nodes when CPU runs high.
4. **EFS-Backed Home Directories** – EFS is mounted at `/home` and `/efs` on every node, so a user's files follow them to whichever node serves their session, and are visible through the Samba gateway.
5. **Mini Active Directory Integration** – A Samba-based mini-AD domain controller provides authentication, groups and DNS.

The deployment runs in four phases:

| Phase | Directory | What it builds |
|-------|--------------|----------------|
| 1 | `01-directory` | Samba 4 mini-AD domain controller, VPC, NAT, credentials in Secrets Manager |
| 2 | `02-servers` | EFS, Windows AD admin host, Linux/Samba gateway, the nodes' IAM instance profile |
| 3 | `03-packer` | Custom AMI: `code-server`, the session broker and the AD join tools |
| 4 | `04-cluster` | ALB with a self-signed certificate, launch template, Auto Scaling Group |

Packer builds the AMI in a public subnet of the lab VPC. Every run of `apply.sh` builds a new, timestamped AMI, and phase 4 always launches from the newest one; `destroy.sh` deregisters them all.

### Build Results

When the deployment completes, the following resources are created:

- **Networking:**
  - A VPC with public and private subnets
  - Internet Gateway and NAT Gateway; the cluster nodes run in the private subnets
  - DNS resolution provided by the Mini-AD domain controller

- **Security & IAM:**
  - Security groups for the ALB (80 and 443 from anywhere) and the nodes (8080 from the ALB only), plus the EFS mount targets and the admin hosts
  - One instance profile, shared by the nodes and the admin hosts: Systems Manager, and read access to the AD administrator secret for the domain join
  - Secrets in AWS Secrets Manager for the AD administrator and the test users

- **Active Directory Server:**
  - Ubuntu EC2 instance running Samba 4 as a Domain Controller and DNS server
  - Seeded with test users and groups

- **Amazon EFS:**
  - Mount targets in the private subnets, mounted with TLS
  - `/home` for every user's files, `/efs` as a shared area
  - `/efs/extensions` provided as a shared staging area for VSIX packages

- **Custom VS Code AMI:**
  - Ubuntu 24.04 with `code-server` (latest release, or the `code_server_version` Packer variable), the session broker and its Python virtualenv
  - PAM stack at `/etc/pam.d/vscode` wired to SSSD for domain authentication
  - Open VSX pinned as the extension gallery

- **VS Code Cluster:**
  - Auto Scaling Group of `m5.large` nodes: starts at 1, adds a node when average CPU stays above 60%, up to 4
  - Each node joins the domain and mounts EFS at boot, then starts the broker
  - Application Load Balancer terminating HTTPS and forwarding to the broker on port 8080, with a one-day stickiness cookie

- **Validation:**
  - `./validate.sh` reports the URL and the admin hosts' addresses, and confirms the broker answers `/healthz`

## How It Works

### The Session Broker

The broker lives at [03-packer/broker/broker.py](03-packer/broker/broker.py) and runs as `vscode-broker.service` on every cluster node: a FastAPI app under `uvicorn`, with exactly one worker because the session registry is held in memory.

| Route | Behavior |
|-------|----------|
| `GET /healthz` | Unauthenticated health check for the ALB target group |
| `GET /login` | Renders the sign-in form |
| `POST /login` | PAM authentication via SSSD, a check for membership in `REQUIRED_GROUP`, then a signed session cookie |
| `GET /session-starting` | Progress page shown while a session spawns |
| `GET /session-status` | JSON readiness poll used by that page |
| `GET /static/<name>` | The sign-in, progress and sign-out page assets |
| `GET /logout` | Stops the user's `code-server` process and clears the cookie |
| everything else | Reverse-proxied to the user's own `code-server` on `127.0.0.1` |

- **Sign-in.** The visible form never submits; [signin.js](03-packer/broker/static/signin.js) copies the credentials into a hidden form, because carrier phishing filters block a plain password form on an `*.elb.amazonaws.com` hostname. The session cookie lasts 12 hours.
- **Launch.** Each session runs as a transient systemd unit named `vscode-<username>`, started with `--uid` so the process holds the user's real POSIX identity, on a free loopback port between 9000 and 9500. A first sign-in takes noticeably longer than later ones, because `code-server` has to initialise the user's state directory before it listens. Rather than block the request, sign-in lands on `/session-starting`, which spawns the session in the background and polls until the port answers. Page navigations that arrive with no live session are redirected there too; sub-resource requests are not, since redirecting a script or font to HTML would corrupt the load.
- **Lifetime.** Sessions with no traffic for `SESSION_IDLE_MINUTES` (120) are stopped. Configuration lives in `/etc/vscode-broker.env`, written at boot by the launch template's user data.
- **Signing out.** `code-server` fills the viewport and knows nothing about the broker, so the broker injects a sign-out button into the workbench document. It mounts into the title bar, just left of the layout controls, and is styled from the workbench's own theme variables so it tracks light, dark and custom themes. If no title bar is found, it floats at the top right. It opens a confirmation dialog, since signing out stops the user's `code-server` process and discards unsaved editor state; files saved to the home directory are unaffected.

The injection is deliberately narrow: it applies only to the root document, never to iframes, workers or sub-resources. The injected `<link>` and `<script>` are same-origin so they satisfy code-server's `'self'` CSP — an inline script would be blocked. If a future code-server release drops `</body>` from that document, the injection is skipped and logged, and the editor still works; only the button disappears.

You can inspect the sessions directly on any node:

```bash
systemctl list-units 'vscode-*'
journalctl -u vscode-jsmith
```

### Node Start-up

The AMI carries everything but the node's identity. At boot, [04-cluster/scripts/vscode_booter.sh](04-cluster/scripts/vscode_booter.sh):

1. Mounts EFS at `/efs` and `/home`.
2. Joins the domain with `realm join`, using the administrator credential from Secrets Manager.
3. Configures SSSD for short names, AD-supplied uid/gid (`ldap_id_mapping = False`) and `/home/<user>`, and admits only members of `vscode-users`.
4. Gives `linux-admins` members sudo.
5. Writes `/etc/vscode-broker.env`, then enables and starts the broker.

The broker is installed in the AMI but not enabled until step 5, so the ALB cannot mark a node healthy before SSSD can resolve AD users.

### Editor State

| State | Location | Survives a new node? |
|-------|----------|----------------------|
| Files in the home directory | `/home/<user>` on EFS | Yes |
| Settings, keybindings, installed extensions, editor layout | `/var/lib/vscode/<user>` on the node's disk | No |

`code-server` keeps its state in SQLite, and SQLite over NFS is a well-known corruption risk, so the whole state directory stays on the node. A user whose session comes back on a different node starts with fresh settings and no extensions; their files are untouched. New state directories are seeded with extension auto-update turned off, since every gallery lookup leaves through the NAT gateway and a slow one stalls the editor.

### Design Trade-offs

These are deliberate choices, not oversights:

- **One session per user, pinned to one node.** The ALB uses cookie stickiness because a user's `code-server` process exists on exactly one instance. If that instance is replaced, the session is gone and the user signs in again. This matches RStudio Server Community — load-balancing sessions across nodes is a paid Workbench feature.
- **Scale-up only.** The group has no scale-down policy. Scaling in would terminate nodes holding live sessions, so the cluster grows under load but does not shrink automatically.
- **Shared nodes, shared kernel.** Users on one node are separated by Unix permissions, not containers or VMs, and `linux-admins` members have root on the node. Keep sudo for people you would trust with every session on it.
- **Editor state is node-local.** See *Editor State*: losing a node costs settings and extensions, never work.
- **`--auth none` on each `code-server`.** Safe only because every instance binds to loopback and the security group admits port 8080 from the ALB alone. The broker is the only path in. Do not widen the bind address.
- **HTTPS with a self-signed certificate.** The ALB terminates TLS using a certificate generated by Terraform and imported into ACM; port 80 only redirects to 443. Over plain HTTP, ISP and carrier security products inspect the page inline, classify the sign-in form as phishing and block it, and some mobile carriers corrupt the WebSocket upgrade that code-server depends on. TLS ends both. The certificate's common name matches the ALB DNS name, so the only browser complaint is the untrusted issuer. To remove it, swap `acm.tf` for a DNS-validated certificate on a domain you control.

### Licensing

This project deliberately uses only the open-source path, which is what makes self-hosting a multi-user service viable:

| Component | License | Notes |
|-----------|---------|-------|
| `code-server` | MIT (Coder) | Installed from the official upstream script |
| Extension gallery | Open VSX (Eclipse) | Pinned explicitly in `/etc/vscode-gallery.env` |
| Session broker | MIT ([LICENSE](LICENSE)) | Written for this project |

**Do not repoint `EXTENSIONS_GALLERY` at Microsoft's Marketplace.** The Marketplace terms permit access only from official Microsoft products, so that one change would make an otherwise lawful deployment non-compliant without altering any code. It is the realistic way this build gets broken — usually by someone chasing a single missing extension.

Microsoft's own `code serve-web` / VS Code Server is under a proprietary license and is **not** interchangeable with `code-server` here, regardless of operating system.

For extensions absent from Open VSX, obtain the `.vsix` from the publisher directly and stage it under `/efs/extensions`, where it is available to every node.

Sideloading is not a workaround for the paragraph above. Gallery terms and extension terms are separate: several Microsoft-published extensions — C/C++, C# Dev Kit, Pylance, Remote Development, Live Share — are licensed for use only with Microsoft's own VS Code products, and that restriction follows the extension regardless of where the VSIX came from. For every other publisher, staging a VSIX obtained from them directly is fine.

### Trust the Certificate

**This step is required, not optional.** The ALB presents a self-signed certificate, and Chrome refuses to register a Service Worker over an untrusted connection — clicking through the interstitial grants you the page, not a valid secure context. VS Code builds every webview on a Service Worker, so without trusting the certificate you lose markdown preview, extension detail pages, notebook rendering, and most extension UI. The symptom is:

```
Error loading webview: Could not register service worker:
SecurityError: ... An SSL certificate error occurred when fetching the script.
```

The core editor, terminal, and file operations work regardless, which is why the problem is easy to miss at first.

Export the certificate from Terraform:

```bash
cd 04-cluster
terraform output -raw vscode_certificate_pem > vscode-alb.crt
```

Then add it to your workstation's trust store:

- **Windows** — `certmgr.msc` → Trusted Root Certification Authorities → Certificates → right-click → All Tasks → Import, and select `vscode-alb.crt`. Restart Chrome.
- **macOS** — `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain vscode-alb.crt`
- **Linux (Chrome)** — `certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n vscode-alb -i vscode-alb.crt`

Each `apply` creates a new load balancer with a new DNS name and therefore a new certificate, so this is repeated per deployment. To avoid it altogether, replace `04-cluster/acm.tf` with a DNS-validated ACM certificate for a domain you control and point a Route 53 alias at the ALB — at the cost of requiring a registered domain to run the lab.

### Users and Groups

When the domain controller is provisioned, a set of sample **users** and **groups** is created from [01-directory/scripts/users.json.template](01-directory/scripts/users.json.template). They are intended for **testing and demonstration purposes**.

#### Groups Created

| Group Name   | gidNumber | Purpose |
|--------------|-----------|---------|
| vscode-users | 10001     | Every user's primary group; grants a VS Code session, and Samba/RDP access on the admin hosts |
| us           | 10002     | Sample regional group |
| india        | 10003     | Sample regional group |
| linux-admins | 10004     | sudo on the cluster nodes and the Samba gateway |

All groups are Security / Universal, created in `CN=Users` of the `vscode.mikecloud.com` domain (NetBIOS `VSCODE`).

#### Users Created and Group Memberships

| Username | Full Name   | uidNumber | gidNumber | Groups Joined |
|----------|-------------|-----------|-----------|---------------|
| jsmith   | John Smith  | 10001     | 10001     | vscode-users, us, linux-admins, Domain Admins |
| edavis   | Emily Davis | 10002     | 10001     | vscode-users, us |
| rpatel   | Raj Patel   | 10003     | 10001     | vscode-users, india, linux-admins, Domain Admins |
| akumar   | Amit Kumar  | 10004     | 10001     | vscode-users, india |

The users get easy-to-type `<word>-<number>` passwords (for example `orange-481920`), stored in Secrets Manager as `<user>_ad_credentials_vscode`.

Membership in **vscode-users** is what grants a session: the broker enforces it with `REQUIRED_GROUP`, on top of the SSSD `simple_allow_groups` restriction applied at domain join. Because it is every test user's primary group, all four can sign in.

To confirm a user resolves, open an SSM session to `efs-samba-gateway` and run `id <username>`. New users follow the usual ADUC plus `uidNumber`/`gidNumber` process; `06-utils/getNextUID.bat` returns the next free UID. A user without a `uidNumber` is invisible to SSSD and cannot sign in.

### Troubleshooting

Open an SSM session to a node (`vscode-instance` in the EC2 console) to run these:

| Command | What it shows |
|---------|---------------|
| `journalctl -u vscode-broker` | The broker: sign-ins, session starts and stops, proxy errors |
| `systemctl list-units 'vscode-*'` | Every live session on this node |
| `journalctl -u vscode-<user>` | One user's `code-server` output |
| `id <user>` | Whether SSSD resolves the user, and their groups |
| `cat /root/userdata.log` | The node's boot: EFS mounts, domain join, broker start |

- **Targets never turn healthy** — check `systemctl status vscode-broker`. Nodes serve `/healthz` only after the domain join completes, so a failed join shows in `/root/userdata.log`.
- **Login fails for a valid AD user** — confirm SSSD resolves them (`id <user>`) and that they are in `vscode-users`.
- **Session starts, page loads, but the editor spins with "handshake timed out"** — check the broker log for `server rejected WebSocket connection: HTTP 403`. code-server refuses a WebSocket upgrade whose `Origin` does not match its own host, as a CSRF defence. The broker rewrites `Origin` to the loopback upstream to satisfy it; if that line is removed the editor will never connect while every HTTP request continues to succeed, because the check applies only to upgrades.
- **Settings and extensions are gone** — the session came back on a different node. This is expected; see *Editor State*.

Expected console noise that is **not** a fault:

| Message | Cause |
|---------|-------|
| `vsda_bg.wasm` / `vsda.js` 404 | Proprietary Microsoft module, absent from the MIT build |
| `github-authentication`, `emmet`, `git-base`, `merge-conflict` 404 | Built-in extensions the OSS build does not bundle |
| `Timed out waiting for authentication provider 'github'` | Follows from the above |
| `open-vsx.org/... 404` | Extension not published to Open VSX — also confirms the gallery pin is working |
| `Service Worker registration SecurityError` | The certificate is not trusted on this machine — see [Trust the Certificate](#trust-the-certificate). Breaks webviews; not cosmetic |

### Clean Up Infrastructure

When you are finished testing, remove all provisioned resources with:

```bash
./destroy.sh
```

This destroys the cluster (load balancer, Auto Scaling Group and its nodes), deregisters every `vscode_ami*` AMI and deletes its snapshot, then destroys EFS and the admin hosts, deletes the Secrets Manager entries without a recovery window, and finally destroys the domain controller and VPC.
